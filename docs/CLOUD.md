# Cloud destinations: Google Drive and Yandex Disk

MediaLatch can save new files to this PC (the default), to Google Drive or to Yandex Disk. Each destination has its own Saving profile: subfolder, folder layout, author/type/site labels and file-name rules. Missing cloud folders are created automatically. A cloud without a saved profile initially inherits the existing PC policy; the first policy save preserves that starting policy separately for each cloud.

**Evidence level.** The code, the vendor request shapes and the failure handling are covered by offline tests against fake servers that follow the vendors' documented contracts. Automated tests use no real account or network write. The owner reported successful Google browser OAuth in Helium. One previously failed 401,816-byte image was then retried from its prepared file in the real installation: Drive confirmed the same pre-generated file ID, size, MIME type, parent and ownership. GIF/video, expiry/recovery and Yandex acceptance are still pending. Native Chrome identity has not been accepted; see [Live acceptance](#live-acceptance-still-owed).

## Using it (end users)

1. Open the MediaLatch page → **Storage**.
2. Press **Sign in with Google** or **Sign in with Yandex**. A browser sign-in window opens; nothing is typed into MediaLatch.
3. Choose the destination for new saves in **Storage**, in **Saving**, or in the toolbar popup (**Save to**). The choice applies at once and only to saves that start afterwards: a save that is already queued or preparing keeps the destination it started with.
4. With a cloud destination selected, use the adjacent **Cloud** control to send media to a connected cloud, or the browser context-menu Save with the selected global destination. Selecting **This PC** hides the inline Cloud actions without disconnecting accounts. Ordinary inline Download and Save all always save locally. Galleries show a compact grid: selected/all locally on the left, selected/all to cloud on the right. A single connected provider saves directly; two providers offer a provider choice. The Downloads list shows the upload stage and says **Saved to Google Drive** only after the provider confirms the stored file.
5. In **Saving**, selecting a destination switches its editable profile and retains unsaved drafts for the other destinations. **Save settings** applies all changed profiles; **Discard changes** restores them. **Universal setup** fills all three drafts with the recommended layout and naming, retaining each destination's subfolder and folder-label overrides. It does not connect accounts or create folders until a file is saved.

Where files go:

| Destination | Location | What MediaLatch can see |
| --- | --- | --- |
| This PC | Browser Downloads or the folder chosen in Saving | n/a |
| Google Drive | A folder named `MediaLatch` in My Drive, then your Saving layout | OAuth: files created/opened with this app (`drive.file`); a supplied token may grant broader access |
| Yandex Disk | The issuing OAuth application’s folder (`Apps/<application name>`), then your Saving layout | Only that folder (`cloud_api:disk.app_folder`) |

Rules that matter:

- A cloud that is not connected, not configured or needs reconnecting is **never** a silent fallback: a save to it is refused with a clear message, and the Storage chooser offers **Manage storage** or an explicit **Use this PC**. Disconnecting does not change the chosen destination for you.
- Existing files are never overwritten: a name that is taken becomes `name (1).ext`. Drive may hold equal names, so MediaLatch looks inside the target folder before it uploads.
- Removing a card from Downloads never deletes a cloud file. Disconnect stops running uploads, forgets the connection and does not delete cloud files. Uploads never change sharing permissions.
- Large uploads survive the extension worker restarting: Drive uploads resume from the server's offset. Yandex Disk's documented upload is a single request and is **not** resumable, so an upload whose outcome is unknown (PUT dispatched, no reliable terminal answer) is kept as *Export uncertain* and is never repeated automatically; files up to 32 MiB are settled automatically when Yandex's SHA-256 matches, larger ones need the owner to check the Disk. A failure before PUT dispatch retries from the prepared file without downloading the media again. After dispatch, timeout, cancellation and server errors remain uncertain until positively reconciled; elapsed time or an absent metadata result is not proof of failure.
- One account per cloud and one backend per save. A job is pinned to the provider, the account and the issuing application (OAuth client): reconnecting a *different* account or application cannot redirect an old job; reconnecting the *same* one lets Retry continue.

### Two ways to connect

**1. Sign in (OAuth, recommended).** Needs the publisher's public application IDs (below). Users only click the button.

**2. Advanced: an access token.** Under **Advanced: use an access token** paste an OAuth access token that was issued to an application of yours. This works even in a build without configured OAuth IDs. An *API key* cannot authorize personal files; a client secret, a service-account key or an ID token do not work either, and the box rejects values shaped like an API key.

Next to the field label, **Get token** opens the provider's official page in a new tab, and the **?** button opens short steps for that provider (Escape or a click outside closes them). Neither action sends, saves or changes anything, and the link never includes the field's value. Google's page is the [OAuth 2.0 Playground](https://developers.google.com/oauthplayground/). Yandex's is its [manual token instructions](https://yandex.ru/dev/id/doc/ru/tokens/debug-token): they need your own OAuth application with `cloud_api:disk.app_folder` and `https://oauth.yandex.ru/verification_code` added as an extra Redirect URI (the extension's own `chromiumapp.org/yandex` redirect stays as it is).

- *Google*: the token needs `https://www.googleapis.com/auth/drive.file`. It is checked with Google's token inspection (`POST https://oauth2.googleapis.com/tokeninfo`, token in the `Authorization` header, no query, no body): the scope, the issuing client (audience) and the remaining lifetime are read, then Drive's `about.user.permissionId` pins the account. It cannot be refreshed in MediaLatch (that needs a client secret); when it expires, paste a new one or sign in.
- *Yandex*: the token needs `cloud_api:disk.app_folder`. Yandex's `login.yandex.ru/info` gives the account and the issuing application; a read-only check of `app:/` shows Disk accepts the token. These checks do not tell MediaLatch the pasted token's granted scopes or expiry, so write access is confirmed by the first real save, a 401 means *Reconnect*, and a 403 is shown as a permission problem, not as expiry. MediaLatch writes no test files.
- A token is kept privately in the extension's IndexedDB. It is not shown again, never part of settings, history, exports, logs, diagnostics or error messages, and the field is cleared when the form closes or the connection succeeds. A failed or cancelled attempt leaves the previous account untouched.
- A token issued to a different application is a different destination: it does not inherit the earlier application's folder or running jobs. For Google `drive.file`, visibility also depends on the issuing application.
- Google token issuers may use either the current hyphenated client ID or a legacy numeric ID (including Google's OAuth Playground). Both remain bound to the verified account and issuing application. Playground tokens are for temporary personal testing, not a replacement for production OAuth registration.

## Privacy and permissions

- New permission: **`identity`** (native Google sign-in or the Google/Yandex OAuth window). It shows no install warning. No `identity.email`, no cookies, no new host permissions (the extension already holds `https://*/*`).
- Data movement: after MediaLatch has downloaded and checked a file, the extension uploads **that staged file** directly from your browser to the provider you chose. The provider is never asked to fetch the source URL, and site cookies or signed media URLs are never sent to it. No MediaLatch server exists in this path.
- Credentials: native Google identity tokens belong to Chrome (MediaLatch stores none); Google web OAuth, Yandex and pasted tokens are stored in the private `medialatch-cloud` IndexedDB, never in `chrome.storage`, which content scripts can observe. Only the extension's own pages can connect or disconnect; the uploader gets a token only on request for the exact provider/account/issuing application of the job.
- The chosen destination (`saveBackend`: `local`, `google_drive`, `yandex_disk`) is a non-secret preference in `chrome.storage.local`. It is not part of exported settings; importing settings cannot turn cloud saving on.
- Public diagnostics and history backups carry no account identity, remote path, upload address or token.

## Publisher setup (OAuth registration)

You need to do this once. The result is **public** client identifiers (including a separate Google Web client for Helium). A client secret is never needed or stored, and there is nothing to paste into source files by hand: use the helper.

```
node tools/configure_cloud.mjs --check
node tools/configure_cloud.mjs --google-client-id 123456789-abcdefgh.apps.googleusercontent.com --yandex-client-id 0123456789abcdef0123456789abcdef
node tools/configure_cloud.mjs --clear-google --clear-yandex
```

It validates the shape of each ID, writes the Google ID to `manifest.json` (`oauth2`, minimum scope `drive.file`) and the Yandex ID to `lib/cloud_config.js`, and refuses anything that looks like a key or a secret. Configure the source for the intended installation ID before producing and accepting a release candidate. Do not patch an already accepted ZIP or dist directory: changing configuration requires a fresh build, provenance and validation in the separate build project. Registration, enabled APIs, consent and publication remain provider-side requirements; a configured public ID alone does not prove sign-in acceptance. A missing ID disables only that provider's OAuth button; its access-token path remains available. `--check` reports the actual configuration.

### Google (Cloud project, Drive API, consent, Chrome Extension client)

Primary sources: Google [Create access credentials](https://developers.google.com/workspace/guides/create-credentials#chrome-extension), [Configure OAuth consent](https://developers.google.com/workspace/guides/configure-oauth-consent), Chrome [Use OAuth 2.0 in extensions](https://developer.chrome.com/docs/extensions/how-to/integrate/oauth).

1. Open the [Google Cloud console](https://console.cloud.google.com/), create a project (for example *MediaLatch*).
2. **APIs & Services → Library → Google Drive API → Enable.**
3. **Google Auth Platform** (OAuth consent): complete **Branding** (app name, support e-mail, developer contact; logo and links as required), **Audience** (*External* for the public; keep *Testing* with your own accounts as test users until you publish) and **Data Access** → *Add or remove scopes* → add **`.../auth/drive.file`** only. Check the scope's current classification on that page; `drive.file` is the narrowest scope that lets the app create and read its own files. Publishing the app (and any verification Google then requires) is Google's process.
4. **Google Auth Platform → Clients → Create client → Application type: Chrome Extension.** Enter the **Item ID** of the extension (32 characters). Create one client per Item ID:
   - **Store extension.** Item ID = the Chrome Web Store Item ID shown in the Developer Dashboard / listing URL. The listing recorded in the project notes is `https://chromewebstore.google.com/detail/medialatch/cimghidldpjhhhngdhigddjfpcofhbmh`, i.e. `cimghidldpjhhhngdhigddjfpcofhbmh` — **confirm it in the Dashboard** before registering. A Store item that you upload keeps its Dashboard ID (do not infer that ID from a developer-signed CRX).
   - **Unpacked / development.** An unpacked extension gets an ID derived from its folder path, so it differs from the Store ID (and between machines). Create a separate client for each actual unpacked or GitHub-CRX ID (copy it from `chrome://extensions`). Do not change `manifest.key` or signing identity to make OAuth fit: that can change the extension ID and its data profile. The Verified CRX Uploads developer signer and the Store item signing identity are distinct; a single OAuth client is usable only for its registered installation ID. Never use or read the private signing PEM for this; registration does not need it.
5. Copy the client ID (`...apps.googleusercontent.com`). Run `node tools/configure_cloud.mjs --google-client-id <id>` in the build for that Item ID. The ID in the manifest must belong to the client created for the ID the extension actually has, or Chrome refuses the sign-in.
6. Native `getAuthToken` requires the browser's Google identity service. [Helium disables GAIA](https://github.com/imputnet/helium/blob/main/patches/ungoogled-chromium/disable-gaia.patch); an existing API function does not prove it can complete. Native interactive requests time out after two minutes; a pending connection can be cancelled without losing the previous account. The access-token path does not use native Google identity.

### Google in Helium: a separate Web application client

1. Keep the Chrome Extension client above. In the same project choose **Clients → Create client → Web application**.
2. Under **Authorized redirect URIs**, add the exact value of `chrome.identity.getRedirectURL('google')`: `https://<actual-extension-id>.chromiumapp.org/google`. Add a separate URI for each Store/dev installation you use. No Authorized JavaScript origin is needed for this redirect-based extension flow. Save the form.
3. Keep `drive.file` and your test account in **Audience → Test users**. Copy only the new public Client ID. Never put the generated client secret into the extension.
4. Run `node tools/configure_cloud.mjs --google-web-client-id <public-web-client-id>`, then reload the extension. When configured, this mode uses `launchWebAuthFlow` instead of native `getAuthToken`; `--clear-google-web` restores native mode without changing its client ID.
5. Sign in opens Google's account/consent window. Closing/denying it, Cancel connection, or a ten-minute deadline ends the attempt; a late answer cannot replace a newer connection. Cancel stops MediaLatch waiting, and does not promise to close a browser-owned window.

This uses Google's documented **browser access-token grant** with a random state and an exact fragment callback, and validates token audience (including `azp` when present), scope, expiry and Drive identity before storing it privately. Google [discourages the legacy direct implicit endpoint](https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow) and recommends its [GIS token dialog](https://developers.google.com/identity/oauth2/web/guides/use-token-model) or a server code flow. MV3 cannot load the remotely hosted GIS script; a server and client secret are outside this local-only implementation. The isolated extension callback is intercepted by the browser; MediaLatch never loads a callback page or logs its URL. This compatibility flow is opt-in through publisher configuration and has **no refresh token**: after expiry the user must explicitly reconnect. Real Google acceptance still needs the registered application and an account; native redirected fixtures alone do not prove it.

### Separate Store and local Google clients

The source retains the existing development Web client as the fallback and maps the Store extension ID `cimghidldpjhhhngdhigddjfpcofhbmh` to the production Web client in `lib/cloud_config.js`. The worker selects by `chrome.runtime.id`; the OAuth callback is still the exact `chrome.identity.getRedirectURL('google')` of that installation. It validates the returned token against the selected client, never a different route's client. The manifest's native Chrome client is registered for the Store Item ID; when a Web client is selected, Web flow takes precedence in Chrome too. Native Chrome testing under another extension ID needs its own manifest client configuration.

```sh
node tools/configure_cloud.mjs --google-web-extension-id cimghidldpjhhhngdhigddjfpcofhbmh --google-web-client-id PUBLIC_PRODUCTION_WEB_CLIENT_ID
node tools/configure_cloud.mjs --check
```

Without `--google-web-extension-id`, setting a Web client updates the fallback only. A different/unmapped ID uses that fallback and still needs a registered callback there. `--clear-google-web --google-web-extension-id ID` removes one mapping; `--clear-google-web` alone clears both fallback and mappings to restore native mode. The tool validates extension IDs and all mapped public client IDs; it never accepts or stores a client secret. Reload the extension after source configuration changes.

For public access, configure **Audience → External → In production** in the production Cloud project and keep the declared `drive.file` scope. Publishing app audience and verifying/publishing branding are separate Google operations; neither is performed by this local tool. Keep development registrations in the development project. No release package is changed by editing the source configuration.

### Yandex (OAuth application, redirect, application folder)

Primary sources: Yandex [OAuth overview](https://yandex.ru/dev/id/doc/ru/register-client), [for user authorization](https://yandex.ru/dev/id/doc/ru/register-auth), [authorization code and PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url), [user information](https://yandex.ru/dev/id/doc/en/user-information), [Disk REST API](https://yandex.com/dev/disk-api/doc/en/).

1. Sign in at [oauth.yandex.ru](https://oauth.yandex.ru/) with an account you will keep, verify the service if Yandex asks (unverified apps show users a warning).
2. **Create app → For user authorization** (the type cannot be changed later). Name, icon (up to 1 MB), contact e-mail.
3. **Platforms: Web services.** Add the **Redirect URI** exactly as the extension computes it: `https://<extension-id>.chromiumapp.org/yandex` (this is `chrome.identity.getRedirectURL('yandex')`; Yandex requires scheme, host, port and path to match). Add one URI for the Store extension ID and one for each unpacked/dev ID you use.
4. **Data access:** add the Yandex Disk REST API permission for the **application folder** (`cloud_api:disk.app_folder`) as the required right. To show free space, also enable the read-only **Disk information** right (`cloud_api:disk.info`); it is requested only on the explicit "Allow storage information" click and never replaces the required one. Nothing broader. If this app type does not offer Disk permissions in the form, record that during live acceptance; the OAuth flow cannot work without that scope.
5. Copy the **Client ID** (32 hex characters). **Do not** use or store the client secret: the flow is authorization code + **PKCE S256** and Yandex does not require a secret when `code_verifier` is sent. Run `node tools/configure_cloud.mjs --yandex-client-id <id>`.
6. Tokens cannot be refreshed without the secret; when one expires MediaLatch shows **Reconnect** and never opens a login by itself during a background save. The app folder lives under *Apps → your application name*.

## How it works (for maintainers)

- `lib/cloud_destination.js` – the pinned destination object `{kind:'cloud', provider, account, issuer, root}`, exact vendor endpoints (`apiUrl`, `driveSession`, `yandexUpload`) and the error catalogue. `lib/cloud_store.js` – private IndexedDB `medialatch-cloud` (accounts, receipts, folder cache). `lib/cloud_http.js` – bounded HTTP (credentials omitted, no redirects, timeouts, bounded body and retry). `lib/cloud_drive.js`, `lib/cloud_yandex.js` – provider clients. `lib/cloud_export.js` – the offscreen exporter: it records a durable receipt (`cloud:job-…`), returns its id at once and uploads detached; the existing manager polling reports progress and the outcome.
- `worker/cloud_accounts.js` – accounts, OAuth/PKCE, token validation, the nonsecret preference, `capture()` (the destination a save pins together with its folder/name policy) and the token provider the uploader asks for. `background.js` routes the `CLOUD_*` messages (trusted extension pages only).
- All four production routes (main, emergency fallback, X/Reddit GIF, Reddit HLS) forward the destination captured by `getSavingSettings` to `managedDownload`; a refused cloud is an error, never a PC save.
- Receipts are never native integer download IDs or chosen-directory receipts, and the pages only see `location: 'cloud'` plus the provider and the uploaded byte count.
- Tests: `tests/test_cloud_providers.js`, `test_cloud_accounts.js`, `test_cloud_manager.js`, `test_cloud_offscreen.js`, `test_cloud_ui.js`, `test_cloud_recovery.js`, `test_cloud_inline.js`, the `45` series in `test_ux_feedback.js` and `--cloud-only` in `test_ui_render.js`.

Google session URIs may include `session_crd` in addition to `uploadType`/`upload_protocol` and `upload_id`; this was observed on the real service. It is an opaque credential: the exact original URI stays in the private receipt, and neither its value nor the URI enters diagnostics. The exact Google origin/path, unique parameter names, bounded alphabets and redirect refusal remain enforced.

Unverified vendor details (documented, not assumed): Yandex lists no upload-host names, so the uploader address must be HTTPS on an `uploader*.dst|disk.yandex.net` host with an `/upload-target/` path (the vendor's sample is `uploader1d.dst.yandex.net`); Yandex does not document resumable uploads; Drive folder-id generation (`files.generateIds`) is used for idempotent creates as documented.

## Free space (account capacity)

The connected Google Drive / Yandex Disk accounts show an advisory "Free {free} of {total}" in one compact **Cloud space** block in the left sidebar, under the section navigation and the Saved volume card, on **every** section (outside the tab content; on a narrow page it sits below the navigation row). Each account is one row with its mark, a thin used-space meter and a small labelled refresh button; a disconnected account is not listed, so no old number outlives it. **Storage** only manages the connection and destination and shows no capacity. The toolbar popup shows only the selected cloud's fresh cached number next to the destination chooser (nothing for this PC, an old number, or a state without figures). **Saved volume and Overview statistics are unchanged**: they count bytes MediaLatch handled, in decimal units, not account storage.

- **What it is.** Account-wide storage as the provider reports it: it includes other apps and, on shared or Workspace plans, the pooled organisation figure. It can lag behind recent uploads, is never subtracted locally after an upload, and never rejects, redirects or delays a save (a real provider quota error stays authoritative).
- **Units.** Capacity uses 1024 steps, as the providers' own pages do (1 TB = 1024 GB), with at most two decimals and no forced trailing zeros: a Google 5 TiB plan (5 497 558 138 880 bytes) reads **5 TB**, not 5.5 TB, and 17.37 GiB less reads about 4.98 TB. A tiny positive amount keeps a suitable unit (never a false "0"). A tooltip on the figures and the **?** popover in the block header state the convention and give the exact localized byte counts. File sizes, downloads and statistics keep their decimal formatting; only capacity uses this (`formatCapacity` in `ui/src/core/cloud.js`; the block and the popup share it).
- **Sources.** Google: `GET /drive/v3/about?fields=storageQuota` (works with `drive.file`); free = `limit − usage` (the account-wide `usage`, not `usageInDrive`); a valid `usage` with no `limit` field is the provider's "no limit". Yandex: `GET https://cloud-api.yandex.net/v1/disk/` (`total_space`, `used_space`). Only nonnegative safe integers are accepted (Google: decimal strings, Yandex: JSON numbers); an absent or malformed value is **unknown**, never 0 and never unlimited. Used above total shows 0 free and a full meter.
- **States.** Not checked yet, checking, available (stale after five minutes, with a note), no limit reported, unknown, access denied, temporarily unavailable. Each is words plus shape, not colour alone. A temporary failure keeps the last good number (it keeps ageing) and says the last check failed.
- **Yandex needs the optional Disk-information right.** The public application page (checked 2026-10-30) listed only `cloud_api:disk.app_folder`, and a read of the Disk root with that scope alone returns 403, which is shown as "this access does not allow reading free space" (the account stays connected, saves are unaffected, and a refresh cannot add rights). Yandex lists `cloud_api:disk.info` separately. The owner first enables **Disk information** in the OAuth application (https://oauth.yandex.ru/). Then, only when the user presses **Allow storage information** in the denied Yandex row (help popover: three steps, the application list and the Disk API access-rights documentation), `CLOUD_CONNECT` carries the strict flag `info: true` and the sign-in adds `optional_scope=cloud_api:disk.info login:email` while `scope=cloud_api:disk.app_folder` stays required (same PKCE, state, redirect and public client; no secret, no broad `disk.read`/`disk.write`, no new host). Normal Sign in requests optional `login:email` for the account label, but no Disk-information right until that explicit choice; once made it is remembered privately in the account record so a later user-triggered reconnect asks again (it is not in settings, export, statuses, diagnostics or inline messages). The flag is only `true` or absent, only for Yandex (anything else is `INVALID_REQUEST`), full page only. The consent is pinned to the connected account (another Yandex account is refused, `CLOUD_ACCOUNT_CHANGED`); closing/declining the consent window or a failed consent keeps the account, destination and number; explicit Cancel preserves the account and destination but invalidates the advisory cache; declining only the optional right leaves the account connected with capacity still denied. A pasted token is never upgraded (a token-method account has no stored consent): get a token with both rights or use the button. After a successful connection the page reads the missing number once without another click and says "Still not allowed" if the rights are not there.
- **When it reads.** One request per provider, only (1) when the full page is opened (or an account finishes connecting) and the number is missing or older than five minutes, (2) on the refresh button, (3) once after confirmed uploads: uploads of a worker that already holds a good number schedule a single follow-up read about ten seconds later per provider, and an album (batch) waits for its last member, so a batch costs one read, not one per file. Switching sections reads nothing and does not remount the block. There is no polling, and opening the popup or `status` never touches the network. A new service worker starts with no number.
- **Safety.** The cache is memory-only and pinned to provider, account, issuing application and connection generation; connecting a different account, disconnecting or cancelling a connection drops it, aborts the read and rejects any late answer. A genuine 401 follows the existing non-interactive recovery (the row becomes "Reconnect needed"); a capacity read never opens a sign-in window. Pages receive only a state, byte counts and the read time (`CLOUD_CAPACITY_REFRESH` is accepted from the full page only; `CLOUD_CHANGED` signals a cache change). Quota figures appear in no log, diagnostic, export, statistics or inline message, and inline capability pushes stay provider-id only.
- **Code.** `lib/cloud_drive.js` / `lib/cloud_yandex.js` `capacity()`, `lib/cloud_destination.js` (`byteCount`, `INFO_SCOPE`), `worker/cloud_accounts.js` (`capacity`, `uploaded`, `connect(provider, info)`), `background.js` (`CLOUD_CAPACITY_REFRESH`, `cloudUploadSettled`), `ui/src/core/cloud.js` (`formatCapacity`, `refreshCapacity`, `refreshStale`, `allowCapacity`), `ui/src/components/app/cloud-capacity.tsx`, mounted by `full-app.tsx` in the sidebar. Tests: the "capacity" and "consent" blocks in `test_cloud_providers.js`, `test_cloud_accounts.js`, `test_cloud_ui.js`, `45j`–`45m` in `test_ux_feedback.js` and `cloud166` in `test_ui_render.js --cloud-only`.

## Inline Save destinations

The ordinary inline Download always saves to this PC, including the chosen local directory, regardless of the popup default. The actions share one neutral graphite dock with a thin outline: the icon saves the selected media, `×N` saves ALL N media of the post (never "item N"). To save one of several images, hover or focus that image and press the icon. Order and Tab order: this PC selected, this PC `×N`, a quiet separator, Cloud selected, Cloud `×N`. A single media item shows icons only; the Cloud group appears only for a locally connected provider and is hidden in This PC mode without disconnecting accounts. A wide tile shows one row, a narrow tile stacks the same groups (PC row above Cloud row); the choice follows the visible media size, never hover, and hover changes only the colour. One provider saves directly; two providers open a compact provider menu. The existing local Save all remains local. Popup and ordinary browser context-menu saves keep the chosen global destination; an inline action never changes that preference.

The content script sends only `local`, `google_drive` or `yandex_disk`. After sender/selected-document admission the worker captures the private account and issuing application once per operation or batch. Synthesized Pixiv page operations and conversion paths retain that captured destination. A later disconnect or account replacement refuses the pinned operation; it never reroutes it to another account or to this PC. Capability messages contain provider enums only, use lifecycle refresh and account-change pushes, and do not request credentials. Missing capability service leaves local Save available.

### Yandex account email

Yandex sign-in requests optional `login:email`; register **Email address** for the OAuth application alongside `cloud_api:disk.app_folder` and the optional capacity right `cloud_api:disk.info`. New permission settings do not change an existing token: grant consent again to receive a new one. The account label uses the provider's `default_email`, never `login` or a constructed address.
