# Подключение облачных хранилищ

В разделе **Хранилища** можно выбрать компьютер, Google Drive или Яндекс Диск. Подключение аккаунта и выбор места сохранения — разные действия. Для каждого места в разделе «Сохранение» есть отдельный профиль: подпапка, структура, названия папок и правила имён файлов. Пока облачный профиль не сохранён, он наследует прежние настройки компьютера; при первом сохранении правил эти исходные настройки закрепляются отдельно для каждого облака.

Выбор места в «Сохранении» переключает его профиль и сохраняет черновики остальных. «Сохранить настройки» применяет все изменённые профили, «Отменить изменения» восстанавливает их. «Универсальная настройка» заполняет удобным пресетом все три черновика, сохраняя отдельные подпапки и переименования папок. Подключение аккаунта и создание папок эта кнопка не выполняет.

Вход через OAuth требует один раз зарегистрировать приложения MediaLatch. Пока они не зарегистрированы, работает дополнительный способ — **«По токену»**. Обычный API-ключ, пароль аккаунта и секрет приложения сюда не подходят.

## Кнопки на сайтах

Обычная inline-кнопка скачивания сохраняет **на компьютер**, в том числе в выбранную локальную папку. Кнопки лежат на одной графитовой панели с тонким контуром. Значок сохраняет выбранное медиа, `×N` — все N медиа поста (не файл номер N). Порядок: выбранное на компьютер, `×N` на компьютер, тихий разделитель, затем облако для выбранного и `×N` в облако. Чтобы сохранить одну из нескольких картинок, наведите курсор или фокус на нужную и нажмите значок. Облачная часть появляется, когда подключён аккаунт и выбрано облачное место сохранения; при выборе «Этот компьютер» она скрывается без отключения аккаунтов. У одиночного медиа есть только значки, без `×N`. На широкой плитке панель идёт в одну строку; на узкой те же группы складываются в две строки (компьютер над облаком). Размер панели зависит только от видимой части медиа, не от наведения. При одном подключённом облаке сохранение начинается сразу; при двух предлагается выбор сервиса. Общий выбор в popup и контекстном меню браузера при этом не меняется.

Каждое начатое сохранение закрепляется за конкретным аккаунтом. Отключение или замена аккаунта не перенаправляет файл в другое место: операция получает отказ. Подпапки и имена определяет профиль выбранного места; уже начатые операции сохраняют принятые при запуске настройки.

## Что нужно сделать владельцу проекта

### 1. Узнать настоящий ID установленного расширения

Откройте `chrome://extensions` (в Helium — `helium://extensions`), включите режим разработчика и скопируйте ID нужной установки MediaLatch.

У версии из магазина, распакованной папки и самостоятельно подписанного CRX ID могут отличаться. Публичная карточка проекта указывает `cimghidldpjhhhngdhigddjfpcofhbmh`; перед регистрацией проверьте её в кабинете Chrome Web Store. Ключ загрузки подтверждённых CRX и ключ, определяющий ID магазинной установки, — разные роли. Не меняйте ключ подписи или `manifest.key` ради OAuth: это может изменить ID и доступ к прежнему профилю данных.

### 2. Зарегистрировать Google

1. Откройте [Google Cloud Console](https://console.cloud.google.com/) и создайте проект MediaLatch.
2. В **APIs & Services → Library** найдите **Google Drive API** и включите его.
3. В **Google Auth Platform** заполните название приложения, контактную почту и сведения о продукте. Для первых проверок оставьте режим **Testing**, добавив свой аккаунт в тестовые пользователи.
4. В **Data Access** добавьте разрешение `https://www.googleapis.com/auth/drive.file`. Оно предназначено для файлов, созданных или открытых через приложение; полный доступ ко всему Диску для обычного входа не нужен.
5. В **Clients → Create client** выберите тип **Chrome Extension** и укажите настоящий **Item ID** из шага 1. Для другого ID установки нужен отдельный клиент.
6. Скопируйте публичный **Client ID**, заканчивающийся на `.apps.googleusercontent.com`. Секрет клиента не нужен.

Официальные инструкции: [клиент Chrome Extension](https://developers.google.com/workspace/guides/create-credentials#chrome-extension), [OAuth в расширении](https://developer.chrome.com/docs/extensions/how-to/integrate/oauth).

### Google в Helium: отдельный веб-клиент

В Helium отключена браузерная служба Google, поэтому клиент **Chrome Extension** и `getAuthToken` могут не открыть окно. Для этой установки используйте отдельный клиент:

1. **Google Auth Platform → Clients → Create client → Web application**. Прежний клиент Chrome Extension оставьте.
2. В **Authorized redirect URIs** добавьте `https://ВАШ-ID-РАСШИРЕНИЯ.chromiumapp.org/google`, подставив настоящий ID установленного MediaLatch. **Authorized JavaScript origins** оставьте пустым. Нажмите **Save**.
3. Скопируйте новый **Client ID**. **Client secret не нужен**, не вставляйте его в расширение.
4. Настройка проекта: `node tools/configure_cloud.mjs --google-web-client-id ВАШ_WEB_CLIENT_ID`. Затем перезагрузите расширение на странице `helium://extensions` и откройте «Хранилища» заново.
5. Нажмите **Войти через Google**. Должно открыться окно выбора аккаунта и согласия. Если приложение в Testing, аккаунт должен находиться в **Audience → Test users**.

Кнопка **«Отменить подключение»** прекращает ожидание без удаления прежнего аккаунта. Запоздавший ответ не заменит новое подключение. Встроенный вход Chrome ограничен двумя минутами, OAuth-окно — десятью; закрытие самого окна контролирует браузер.

Веб-вход выдаёт временный access token без автоматического продления: по истечении срока потребуется **«Подключить снова»**. Это совместимый режим через документированный браузерный token flow; Google рекомендует более современный GIS или серверный code flow, а удалённый GIS-скрипт и сервер с секретом в расширение не добавлены. Технические ограничения и ссылки — в [CLOUD.md](CLOUD.md#google-in-helium-a-separate-web-application-client). Реальное согласие Google остаётся отдельной проверкой.

### Разные Google-клиенты для магазина и локальной установки

В исходнике сохранён прежний Web-клиент разработки, а для магазинного ID `cimghidldpjhhhngdhigddjfpcofhbmh` в `lib/cloud_config.js` указан отдельный production Web-клиент. Расширение выбирает его по своему настоящему `chrome.runtime.id`; адрес возврата по-прежнему определяется этой установкой через `chrome.identity.getRedirectURL('google')`. Полученный токен проверяется именно для выбранного клиента. Native-клиент в manifest зарегистрирован для магазинного ID; настроенный Web-вход имеет приоритет и в Chrome. Для проверки native-входа с другим ID нужен соответствующий клиент в manifest.

```sh
node tools/configure_cloud.mjs --google-web-extension-id cimghidldpjhhhngdhigddjfpcofhbmh --google-web-client-id ПУБЛИЧНЫЙ_PRODUCTION_WEB_CLIENT_ID
node tools/configure_cloud.mjs --check
```

Без `--google-web-extension-id` команда меняет только запасной Web-клиент. Другой ID установки использует этот клиент и требует зарегистрированного там адреса возврата. `--clear-google-web --google-web-extension-id ID` удаляет одну привязку; `--clear-google-web` без ID очищает все Web-клиенты и возвращает native-режим. Секрет клиента нигде не нужен. После изменения исходника перезагрузите расширение.

Для публичного входа в production-проекте Google выберите **Audience → External → In production** и оставьте разрешение `drive.file`. Публикация аудитории и проверка/публикация бренда — разные действия в Google; локальная команда их не выполняет. Клиенты разработки остаются в проекте разработки. Изменение исходника не обновляет ранее подготовленный архив или расширение в магазине.

### 3. Зарегистрировать Яндекс

1. Откройте [Яндекс OAuth](https://oauth.yandex.ru/) и создайте приложение **для авторизации пользователей**.
2. Укажите название, значок и контактную почту. Выберите платформу **Веб-сервисы**.
3. Добавьте Redirect URI: `https://ВАШ-ID-РАСШИРЕНИЯ.chromiumapp.org/yandex`. Замените ID на настоящий. Для нескольких установок добавьте отдельный адрес каждой.
4. В доступах найдите **Яндекс Диск REST API → Папка приложения** (`cloud_api:disk.app_folder`). Если кабинет не предлагает это разрешение для выбранного типа приложения, этот этап нужно отдельно проверить; другой доступ автоматически не подставляем. Чтобы показывать свободное место, включите ещё право только для чтения **«Информация о Диске»** (`cloud_api:disk.info`): оно запрашивается лишь по явному нажатию «Разрешить сведения о хранилище» и не заменяет обязательное. Ничего шире.
5. Скопируйте публичный **Client ID** — 32 шестнадцатеричных символа. Секрет не присылайте: реализован вход по коду с PKCE S256.

Официальные инструкции: [регистрация приложения](https://yandex.ru/dev/id/doc/ru/register-auth), [код авторизации и PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url).

### 4. Передать только публичные идентификаторы

Для настройки нужны публичные Client ID и настоящий ID установки; у Google для Helium используется отдельный Web Client ID. Токены, пароли, приватный PEM и секреты OAuth присылать не требуется.

В проекте есть помощник:

```powershell
node tools/configure_cloud.mjs --check
node tools/configure_cloud.mjs --google-client-id ВАШ_GOOGLE_CLIENT_ID --yandex-client-id ВАШ_YANDEX_CLIENT_ID
```

Настройка выполняется до сборки нового кандидата. Уже принятый ZIP не редактируется: после изменения публичных ID нужны новая сборка и проверка. Для магазинной и локальной установки с разными ID Google могут понадобиться отдельные конфигурации.

## Подключение по токену

В строке сервиса нажмите **«По токену»**, вставьте личный OAuth access token и нажмите **«Подключить по токену»**. Поле скрывает символы. После успешного подключения или закрытия оно очищается. Токен хранится в приватной базе расширения и не включается в экспорт настроек, историю или диагностические отчёты.

Рядом с названием поля кнопка **«Получить токен»** открывает официальную страницу сервиса в новой вкладке, а кнопка **«?»** показывает короткие шаги для этого сервиса (Escape или щелчок вне подсказки закрывает её). Ни то ни другое ничего не отправляет, не сохраняет и не меняет, а в ссылку не попадает введённое значение. У Google это [OAuth 2.0 Playground](https://developers.google.com/oauthplayground/). У Яндекса — [инструкция по ручному получению токена](https://yandex.ru/dev/id/doc/ru/tokens/debug-token): нужно своё OAuth-приложение с `cloud_api:disk.app_folder` и дополнительным Redirect URI `https://oauth.yandex.ru/verification_code` (собственный redirect расширения `chromiumapp.org/yandex` остаётся).

- **Google:** нужен access token с `drive.file` (или уже выданным более широким Drive-доступом). MediaLatch проверяет издателя, срок, права и аккаунт. Когда токен истечёт, нужен новый или обычный вход.
- **Яндекс:** нужен токен с `cloud_api:disk.app_folder`. Проверяются аккаунт, приложение-издатель и доступ к API. Эти проверки не позволяют MediaLatch определить полный набор прав и срок действия вставленного токена; возможность записи подтвердит первое сохранение. Папка принадлежит приложению, выдавшему токен, поэтому при чужом Client ID она может называться иначе, чем MediaLatch.

## Свободное место в аккаунте

Подключённые Google Drive и Яндекс Диск показывают справочное «Свободно {free} из {total}» в одном компактном блоке **«Место в облаке»** в левой боковой панели, под навигацией и карточкой «Сохранённый объём», на **каждом** разделе (вне содержимого вкладок; на узкой странице блок стоит под строкой навигации). Каждый аккаунт — одна строка со значком сервиса, тонкой полосой занятого места и небольшой подписанной кнопкой обновления; отключённый аккаунт не показывается, поэтому старое число не переживёт отключение. Страница **«Хранилища»** только управляет подключением и местом сохранения и объём не показывает. В окне расширения рядом с выбором места сохранения виден только свежий кэшированный объём выбранного облака (для этого компьютера, устаревшего числа или состояния без цифр ничего нет). **«Сохранённый объём» и статистика не меняются**: они считают байты, обработанные MediaLatch, в десятичных единицах, а не занятое место аккаунта.

- **Что это.** Объём всего аккаунта по данным сервиса: он включает другие приложения и общие (в том числе Workspace) тарифы, может отставать от недавних загрузок, не уменьшается локально после загрузки и никогда не отклоняет, не перенаправляет и не задерживает сохранение (настоящая ошибка квоты от сервиса остаётся главной).
- **Единицы.** Объём считается шагами по 1024, как на страницах самих сервисов (1 ТБ = 1024 ГБ), не более двух знаков после запятой и без лишних нулей: тариф Google 5 ТиБ (5 497 558 138 880 байт) показывается как **5 ТБ**, а не 5,5 ТБ, а на 17,37 ГиБ меньше — примерно 4,98 ТБ. Малое положительное значение получает подходящую единицу (не ложный «0»). Подсказка к цифрам и всплывающее окно **?** в заголовке блока объясняют правило и дают точное число байт. Размеры файлов, загрузки и статистика остаются в десятичных единицах; шаги по 1024 только у объёма аккаунта (`formatCapacity` в `ui/src/core/cloud.js`; блок и окно расширения используют одну функцию).
- **Источники.** Google: `GET /drive/v3/about?fields=storageQuota` (работает с `drive.file`); свободно = `limit − usage` (общий `usage`, а не `usageInDrive`); корректный `usage` без поля `limit` означает «без лимита». Яндекс: `GET https://cloud-api.yandex.net/v1/disk/` (`total_space`, `used_space`). Принимаются только неотрицательные безопасные целые (Google: десятичные строки, Яндекс: числа JSON); отсутствующее или некорректное значение — «неизвестно», а не 0 и не «без лимита». Если занято больше лимита, свободно 0 и полоса заполнена.
- **Состояния.** Ещё не проверялось, проверка, есть данные (через пять минут помечаются как возможно устаревшие), лимит не указан, неизвестно, доступ запрещён, временно недоступно. Состояние всегда выражено словами и формой, не только цветом. При временной ошибке остаётся последнее удачное число (оно продолжает стареть) с пометкой, что последняя проверка не удалась.
- **Яндексу нужно необязательное право «Информация о Диске».** Публичная страница приложения (проверено 2026-10-30) показывала только `cloud_api:disk.app_folder`, и чтение корня Диска с одним этим правом возвращает 403: показывается «этот доступ не позволяет узнать свободное место» (аккаунт остаётся подключённым, сохранение работает, а обновление права не добавит). `cloud_api:disk.info` Яндекс перечисляет отдельно. Сначала владелец включает право **«Информация о Диске»** в OAuth-приложении (https://oauth.yandex.ru/). Затем, только если пользователь нажал **«Разрешить сведения о хранилище»** в строке Яндекса (справка из трёх шагов, список приложений и документация по правам Disk API), `CLOUD_CONNECT` несёт строгий флаг `info: true`, а вход добавляет `optional_scope=cloud_api:disk.info login:email`, оставляя `scope=cloud_api:disk.app_folder` обязательным (те же PKCE, state, redirect и публичный клиент; без секрета, без широких `disk.read`/`disk.write`, без нового адреса). Обычный вход запрашивает опциональный `login:email` для подписи аккаунта, но не право чтения объёма до этого явного выбора; сделанный выбор приватно хранится в записи аккаунта, чтобы следующее повторное подключение по действию пользователя снова спросило (в настройках, экспорте, статусах, диагностике и сообщениях сайтам его нет). Флаг — только `true` или отсутствует, только для Яндекса (иначе `INVALID_REQUEST`), только полная страница. Согласие привязано к подключённому аккаунту (другой аккаунт Яндекса отклоняется, `CLOUD_ACCOUNT_CHANGED`); закрытие окна согласия, отказ в нём или неудача сохраняют аккаунт, место сохранения и число; явная кнопка отмены сохраняет аккаунт и место сохранения, но сбрасывает справочный кэш; отказ только от необязательного права оставляет аккаунт подключённым, а объём — недоступным. Вставленный токен не обновляется: получите токен с обоими правами или нажмите кнопку. После успешного подключения страница один раз читает недостающее число без дополнительного клика и пишет «по-прежнему нельзя», если прав нет.
- **Когда читается.** Один запрос на сервис: (1) при открытии полной страницы (или когда аккаунт закончил подключение), если числа нет или оно старше пяти минут; (2) по кнопке обновления; (3) один раз после подтверждённых загрузок: фоновый процесс, у которого уже есть удачное число, планирует один повторный запрос примерно через десять секунд на сервис, а пакет (альбом) ждёт последний файл — запрос один на пакет, а не на файл. Переключение разделов ничего не читает и не пересоздаёт блок. Опроса по таймеру нет; открытие окна и `status` в сеть не ходят. Новый фоновый процесс начинает без числа.
- **Безопасность.** Кэш только в памяти и привязан к сервису, аккаунту, приложению-издателю и поколению подключения; подключение другого аккаунта, отключение или отмена подключения сбрасывают его, прерывают чтение и отклоняют любой поздний ответ. Настоящий 401 идёт по прежнему неинтерактивному восстановлению (строка станет «Нужно подключить заново»); чтение объёма никогда не открывает окно входа. Страницы получают только состояние, байты и время чтения (`CLOUD_CAPACITY_REFRESH` принимается только от полной страницы; `CLOUD_CHANGED` сообщает об изменении кэша). Объёмы не попадают в журналы, диагностику, экспорт, статистику и сообщения кнопок на сайтах; рассылка возможностей облака на сайты по-прежнему содержит только идентификаторы сервисов.

## Что проверить после настройки

1. Войти, выбрать хранилище, сохранить изображение, GIF и видео. Проверить реальные файлы, имена и подпапки в облаке.
2. Проверить Google в Chrome и отдельно веб-вход в Helium: окно выбора аккаунта, согласие, отказ, отмену, повторный вход и реальную загрузку. Способ по токену не зависит от Google Identity браузера.
3. В процессе загрузки поменять место для новых сохранений: уже начатый файл должен попасть в прежнее место.
4. Повторить имя файла: прежний файл не должен перезаписаться. Проверить отмену, отключение аккаунта, просроченный токен и повтор после известной ошибки.
5. Google восстанавливает загрузку по сохранённому ID и смещению сервера. У Яндекса после отправки неизвестный результат нельзя безопасно повторять вслепую: точное совпадение SHA-256 подтверждается для файлов до 32 МиБ; иначе сначала проверьте облако вручную.

Удаление записи в менеджере не удаляет файл из облака. Неизвестный результат не считается успешным сохранением. Автоматические тесты используют подменённые API. Отдельно подтверждены вход Google в Helium и повторная запись одного подготовленного изображения 401 816 байт в реальный Drive: проверены ID файла, размер, тип и папка. GIF, большие видео, истечение токена, восстановление и Яндекс остаются отдельной приёмкой.

Техническое описание: [CLOUD.md](CLOUD.md).

### Email аккаунта Яндекса

При входе запрашивается опциональное право `login:email`. В OAuth-приложении включите **Доступ к адресу электронной почты** вместе с `cloud_api:disk.app_folder` и опциональным `cloud_api:disk.info` для объёма. Изменение прав в кабинете не меняет прежний токен: нужно повторное согласие и новый токен. Подпись аккаунта берётся только из `default_email`, без подстановки логина или выдуманного адреса. При отказе или отсутствии почты выводится **Email недоступен**; сохранение файлов продолжает работать. Адрес хранится как приватная информация аккаунта и не попадает в диагностику или экспорт настроек. Прежний сохранённый username скрывается до нового подключения с настоящим email.


Проверка владельца: перед выпуском 3.0.7 владелец сообщил о локальном тесте; скриншоты показывают оба подключённых аккаунта, свободное место и один файл X в папке Яндекс Диска. Это отдельный результат для одного сценария, а не приёмка всех форматов, квот, отзыва доступа или входа из магазина.
